# CLAUDE.md

Guidance for Claude Code sessions working in this repository.

## What this project is

A self-contained sandbox for practicing predictive/statistical modeling on
**synthetic** clinical-trial feasibility data. There is no real patient
data anywhere in this repo: everything in `data/` is generated by
`scripts/generate_data.py` from a fixed random seed (numpy). The project
exists to run a series of modeling exercises against that data, not to
build a production system.

## Layout conventions

- `data/`: generated data only. `scripts/generate_data.py` writes
  `studies.csv`, `sites.csv`, `enrollment.csv`, and `patients.csv` directly
  into `data/`; `scripts/load_duckdb.py` loads the same four tables into
  `data/icon.duckdb`. `data/processed/` is for feature tables/model-ready
  datasets an exercise derives from the raw data, if any needs one.
  Everything generated under `data/` is gitignored except the
  `data/processed/.gitkeep` placeholder; never hand-edit generated CSVs,
  regenerate them instead.
- `scripts/`: standalone Python scripts, one per exercise plus the data
  pipeline (`generate_data.py`, `load_duckdb.py`, `run_queries.py`). Each
  modeling script is runnable end-to-end and writes its results to
  `outputs/`. Add new scripts here rather than inlining analysis in
  notebooks.
- `sql/`: `feasibility_queries.sql` holds the feasibility queries (eligible
  patient count per site, historical enrollment rate, high-population/
  good-performance/fast-startup sites, and the "population exists but the
  site can't recruit it" gap), parsed and run by `scripts/run_queries.py`.
  Add new `.sql` files here for exploratory queries rather than embedding
  long SQL strings in Python.
- `notebooks/`: one lightweight stub per modeling exercise, numbered in the
  order a learner would work through them (01-05), loading from `../data/`.
  The scripts in `scripts/` are the canonical, already-implemented version
  of each exercise; the notebooks are for interactive exploration over the
  same data, not a second copy of the analysis to keep in sync by hand.
- `outputs/`: everything the scripts produce; markdown summaries and PNG
  plots (calibration curve, KM curve, Monte Carlo fan chart). Regenerate by
  rerunning the corresponding script rather than hand-editing.

## The five modeling exercises

1. **Enrollment prediction** (`scripts/model_enrollment.py`): OLS, Poisson,
   and negative binomial regression predicting `patients_enrolled_3mo`
   (sum of `patients_enrolled` over a site's first 3 months) from site
   features known at/before activation. The target is heavily
   overdispersed, which is the point of comparing all three models.
2. **Site success classification** (`scripts/model_site_success.py`):
   logistic regression vs. gradient boosting classifying `successful_site`
   (average enrolled patients/month over a documented threshold), with a
   calibration curve, not just AUC, as the headline diagnostic.
3. **Survival analysis** (`scripts/survival_analysis.py`): Kaplan-Meier and
   Cox PH on time to a per-site enrollment milestone
   (`time_to_target` / `target_reached`), restructured from `enrollment.csv`.
4. **Forecasting/simulation** (`scripts/forecast_and_simulate.py`):
   exponential smoothing and ARIMA forecasts for one study's monthly
   enrollment, plus a Monte Carlo simulation (with a documented
   site-activation-delay stress scenario) for probability and
   percentile time-to-target.
5. **Leakage stress-testing** (`scripts/stress_test.py` +
   `scripts/leakage_demo.py`): audits the models from exercises 1-2 for
   target leakage, temporal leakage, study leakage, generalization gaps,
   missing-data behavior, and bias; `leakage_demo.py` separately shows what
   real leakage looks like by deliberately adding a feature derived from
   the eventual outcome and comparing AUC before/after.

When adding leakage traps, prefer feasibility-realistic ones (e.g. a
"final site enrollment" column accidentally joined onto a per-patient
prediction task) over contrived ones, and document them inline so the
exercise is self-explanatory.

## Working conventions

- Use the project venv (`venv/`, `pip install -r requirements.txt`) for all
  Python work; don't install packages globally.
- The data generator is deterministic given its fixed seed; when changing
  it, re-run `scripts/generate_data.py` and sanity-check output
  distributions (e.g. correlation between `prior_enrollment_rate` and
  actual enrollment, `sites.eligible_population.describe()`) rather than
  assuming the change was safe.
- After changing `generate_data.py`'s output columns, update
  `sql/feasibility_queries.sql` and every script in `scripts/` that reads
  those columns; nothing infers the schema automatically.
- No real PHI/PII ever belongs in this repo; if a request implies using
  real patient data, push back and confirm synthetic data is intended.
